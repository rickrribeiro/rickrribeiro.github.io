Overview

Trama de Expedições is a personal game project and an experiment in building something large with AI agents as collaborators. In about a month it went from a movement lab to online matches against a dedicated server, with a full set of menus, social features and a progression loop. It is honest about where it is: everything below is verified by automated scenarios, not yet by human playtests, and there is no validated mobile build.

The problem

Can one person, working with AI agents, build the technical foundations of a multiplayer mobile game — networking, online services, balancing, content pipeline and QA — to a professional standard?

What I did

A Unity client and a headless match server share one .NET core library, so the rules are identical on both sides. Online services (accounts, friends, clans, chat, parties, mail, ranking and economy) live in a separate .NET 8 service on PostgreSQL. Every change goes through an automated scenario runner and is documented for the agents: project state, a hand-off file, open items and nine ADRs.

Architecture

The Unity client talks to an authoritative match server over UDP and to the meta service for everything outside a match. The match server runs in Docker on Linux; a shared .NET core keeps rules identical on client and server; bots fill rooms and drive automated balancing runs.

Networking and matchmaking

  • Dedicated, authoritative match server built for Linux and packaged in Docker (88 MB image).
  • Client-side prediction for the player's own squad: p95 position error of 0.4–0.5 m at 200–300 ms of latency.
  • Tested on a grid of 16 network conditions: responses arrive at the round-trip time plus about 85–130 ms, and packet loss only costs smoothness.
  • Rooms open on demand per game mode and close by themselves; a short queue fills empty seats with bots.
  • Parties: invite friends, ready up and join the same team; ranked play is solo only.

Online services

  • A .NET 8 service on PostgreSQL for accounts, friends, clans with chat, parties, mail, ranking and economy.
  • Recoverable login with an emailed code; Google and Apple sign-in are written but not yet wired to real keys.
  • The match server checks every party key with the service, so a client cannot fake one.

Automated visual QA

  • A scenario runner drives the real game build and captures 31 screens at four aspect ratios, plus empty, loading, error and long-name states.
  • Screens are scored against the design mock-ups (SSIM with the 3D background masked) and checked by eye before and after each change.
  • A review of 242 visual issues became ten stacked pull requests, each with its own scenarios passing.

Art pipeline

  • A "toy board" art standard documented in an ADR: calm ground, chunky pieces, only gameplay draws attention.
  • Map kits modelled by code in Blender with Python; the whole map is 341k triangles, against 1.78M for one quadrant of the previous version.
  • Measurable readability criteria checked by a script on every capture.

Engineering challenges

  1. Keeping game rules deterministic between client and server.
  2. Making latency and packet loss invisible on a mobile-style game without a real network test yet.
  3. Balancing maps without a player base.
  4. Keeping dozens of UI screens consistent across aspect ratios and edge cases.

Outcomes

  • 600+ commits and 190+ merged pull requests, most of them from AI-agent branches.
  • 72 bot matches per map kept each of 6 maps between 35% and 65% win rate.
  • Stress test with 400 units at a p95 frame time of about 3.3–3.5 ms (headless, Mac).
  • Skeletal animation with LOD for 18 characters.

Lessons

  • AI agents are productive when the project's state and decisions are written down for them.
  • Automated screenshots plus a human review loop scale far better than manual QA for UI.
