Overview

Group Wave Enterprise builds marketing-automation products. I joined to work across the whole stack — NestJS backend, React frontend and the infrastructure underneath — while the platform was being redesigned, and ended up owning three areas: the platform itself, the campaign-automation engine and an internal financial system.

The problem

The product had grown as a set of microservices that were expensive to evolve and operate for the size of the team. Some workflows were slow, CPU-heavy work competed with request handling, builds shared resources with production, and there were no shared standards for repositories, pipelines, testing or observability.

What I did

Together with an external software-architecture consultant I helped define the new platform architecture and contributed to the migration to a modular React/NestJS monolith. In parallel I took ownership of the platform — Kubernetes, CI/CD, databases, observability and security — and built the product areas described below, each change small and documented (decisions as ADRs, operations as runbooks).

Architecture

Simplified view. The NestJS monolith pushes heavy work to workers — one deployment per queue, scaled on queue depth by KEDA — and reaches PostgreSQL through PgBouncer. Redis, RabbitMQ and MinIO run next to it on Kubernetes; Jenkins builds and deploys; OpenTelemetry, Prometheus, Grafana and Loki observe everything.

Platform & reliability

Most of my work happened below the product: making the platform cheaper to run, safer to change and observable.

  • CI/CD rebuilt in three phases — GitHub Actions → self-hosted ephemeral runners on Kubernetes → standalone Jenkins provisioned with Ansible and configured as code — with CI isolated from production, priority per branch and only the affected tests (with diff coverage) on pull requests. Profiling cut backend PR time by 26% (lint + tests 380 s → 244 s), the backend image by ~41% (2.5 GB → 1.5 GB) and one build step from ~285 s to ~5 s.
  • Workers split into one deployment per queue, each with its own resources and connection budget, autoscaled on queue depth with KEDA.
  • A PostgreSQL connection-management project: PgBouncer, per-worker connection budgets, cleanup of idle transactions and memory tuning — plus automated, encrypted off-site backups and audited, least-privilege database access for engineers.
  • Observability end to end: OpenTelemetry traces correlated with logs (and a copyable trace ID in the UI), Prometheus with Thanos, Loki, Grafana dashboards, Grafana Faro for real-user monitoring, SLOs with multi-window burn-rate alerts, runbooks and post-mortems.
  • Security baseline: secrets out of the repositories, secret scanning and static analysis in CI and pre-commit, SSO for internal tools and a hardened ingress.
  • Incident response and audits: root-cause analysis of production incidents (table bloat, disk I/O saturation — including a query-logging loop growing ~20 GB/h that competed with the database's write-ahead log — and a runaway budget automation), each turned into fixes, guardrails and alerts; plus a multi-tenant readiness audit with a GO/NO-GO assessment and a phased 13-sprint plan.

Campaign automation engine

Media buyers describe rules — when a campaign's metrics cross a threshold, change its budget or status — and the platform runs them on a schedule.

  • A rules engine with conditions on sales, spend and checkout data, budget and status actions, time-window scheduling and manual or automatic target selection.
  • Execution runs on dedicated workers; every run records the rule version in force, what happened to each target and why nothing happened when a rule was skipped.
  • A versioned external API with per-tenant keys, rate limiting and a published OpenAPI contract, so other systems can read the same data.

Internal financial platform

An internal system that replaced spreadsheets for the group's finance team. I led its design and built most of it, backend and frontend. Security details are deliberately kept general here.

  • Ledger and ERP: bank and card-account sync through queues with per-account progress, multi-currency P&L at daily exchange rates, CSV import and export, and automatic matching of internal transfers.
  • A categorization rules engine where the most specific rule wins and conflicts are shown before saving, plus bulk categorization and suggestions.
  • Finance operations: commissions with monthly close snapshots, contractor payroll, invoices, tax forecasting, performance bonuses, accounting documents, a partner registry and an activities suite.
  • Defense in depth: tenant isolation enforced by the database as well as the application, encrypted and masked sensitive data with audited access, a tamper-evident audit trail, step-up authentication for critical actions, time-bound access with reports and alerts, and security checks in CI.

Engineering challenges

  1. Migrating from microservices to a modular monolith while product features kept shipping.
  2. Separating CPU-bound jobs from request handling without duplicating work — solved with per-queue workers, autoscaling and BullMQ job deduplication.
  3. Keeping database connections under control as the number of workers grew.
  4. Building a financial system where a security mistake is expensive, without slowing the finance team down.

Outcomes

  • Application workflows more than 70% faster through refactoring, caching, BullMQ job deduplication and dedicated workers.
  • 1,000+ merged pull requests in about six months across infrastructure, backend and frontend.
  • Backend PR pipeline 26% faster and a ~41% smaller backend image.
  • CI isolated from production, faster feedback on PRs and every pipeline change documented as an ADR.
  • Observability with SLOs and alerts that are tied to runbooks and post-mortems.
  • An internal financial platform in daily use, plus a campaign-automation engine and an external API.
  • A shared Claude Code RAG knowledge base and reusable LLM skills/agents for the engineering team.

Lessons

  • A modular monolith gives a small team most of the isolation of microservices with a fraction of the operational cost.
  • Platform engineering pays off fastest when it is encoded in templates and pipelines, not in documents.
  • Writing each decision down as an ADR is what made it possible to change CI three times without losing the reasoning.
